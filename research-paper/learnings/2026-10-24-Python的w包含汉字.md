# Python 的 `\w` 包含汉字：数字门禁在中文稿上整句漏检

## 问题

`check_paper.py` 初版用 `(?<![\w.])…(?![\w])` 给结果数字划边界，英文夹具全绿。
对抗方一句 `灵敏度为91.5%，AUC为0.912。样本量n=412例` 就打穿了：Python 3 的 `\w`
是 Unicode 感知的，汉字也算「单词字符」，紧贴汉字的数字一个都没匹配上——
中文稿里任何未入账的数字都以 exit 0 放行。skill 明明附带中文 scaffold。

同一轮还发现第二个同族问题：剥离 `[...]` 时把所有方括号都剥了，
`[95% CI 0.71, 0.80]` 这种医学写作里最常见的方括号置信区间整体豁免。

## approach

- 边界只认 ASCII：`(?<![A-Za-z0-9_.])` / `(?![A-Za-z0-9_])`。research-proposal 的
  叙述式引文 `根据Smith (2020)` 撞上同一个坑，同样改为 ASCII 边界。
- 只剥离「确定不是结果数字」的东西：`[PENDING…]`/`[UNVERIFIED…]` 旗标、citekey 组、
  顺序编码引文 `[1]`、URL/DOI、行内代码；链接只剥目标、保留链接文字。
- 两条都有回归测试（`test_numbers_in_chinese_prose_are_checked`、
  `test_bracketed_confidence_interval_is_checked`）和对应变异体。

## 结论

**正则里的 `\w` 在 Python 3 不等于 `[A-Za-z0-9_]`。** 凡是要在中英混排文本上划
「词边界」的门禁，边界必须显式写 ASCII 类；夹具必须至少有一行中文。
「剥掉干扰项」的预处理要列白名单，不要用一个宽正则一刀切——切掉的往往正是要查的东西。
